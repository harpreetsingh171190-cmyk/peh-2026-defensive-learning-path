# 29. Modern Web and API Security (2026)

## Learning goals
Understand how to assess web applications and APIs in a controlled lab, explain impact, and propose fixes. Use the OWASP Web Security Testing Guide and OWASP API Security Project as living references.

## Test planning
1. Get written permission and define domains, IPs, accounts, test windows, request limits, and prohibited actions.
2. Build an inventory of routes, API versions, roles, authentication methods, and data types.
3. Record normal behavior before testing. Use a test account and synthetic records.
4. Keep each test reproducible and link evidence to a finding ID.

## Core test areas
- Authentication: account lifecycle, reset flows, MFA enforcement, session rotation and logout.
- Authorization: object-level and function-level access control; verify with two test users and dummy objects.
- Input handling: SQL/NoSQL injection, command injection, path traversal, template injection, and unsafe deserialization in deliberately vulnerable labs.
- Browser security: XSS, CSRF, CORS, clickjacking, CSP, cookie flags, and mixed content.
- File handling: extension/content validation, size limits, storage isolation, malware scanning, and safe download headers.
- API-specific checks: object/property-level authorization, excessive data exposure, mass assignment, resource consumption, inventory/version management, and unsafe trust in upstream APIs.
- OAuth/OIDC and tokens: redirect URI validation, state/nonce, audience/issuer, expiry, key rotation, and secure storage.
- GraphQL: schema exposure decisions, authorization per resolver, query depth/complexity limits, and error leakage.
- Business logic: duplicate transactions, workflow skipping, race conditions, and abuse of quotas.

## Tooling workflow
Use an intercepting proxy such as Burp Suite Community or OWASP ZAP against your own local lab. Use browser dev tools and `curl` to understand requests. Keep a low request rate and avoid destructive payloads.

Example: inspect a local service only:
```bash
curl -i --max-time 5 http://127.0.0.1:8080/
```

Example: save a response for review without sending secrets:
```bash
curl -sS --max-time 5 http://127.0.0.1:8080/api/health -o response.json
```

## Remediation patterns
Enforce authorization server-side for every object and property; validate inputs using allowlists and typed schemas; use parameterized queries; limit request size, pagination, and expensive operations; keep secrets out of URLs/logs; configure secure cookies and appropriate CSP; test fixes with regression cases.

## Practice exercise
In a local intentionally vulnerable app, create two users and two dummy records. Test whether user A can read or edit user B's record. Document the authorization gap, then add a server-side ownership check and write a regression test. Do not test real services without explicit permission.
