# 32. Android Mobile Application Security

## Scope and setup
Use an emulator, your own test device, or a deliberately vulnerable training app. Obtain permission before assessing any app you do not own. Do not bypass protections on someone else's device or extract another person's data.

## Static review
- App manifest: permissions, exported activities/services/receivers/providers, deep links, backup settings, and debug flags.
- Storage: hard-coded keys, tokens, personal data, logs, and insecure local databases/preferences.
- Network: cleartext traffic, certificate validation, trust configuration, and sensitive data in URLs.
- Components: intent validation, file providers, content providers, and pending-intent mutability.
- Dependencies: outdated SDKs/libraries and known vulnerabilities.
- Build/release: debug signing, unnecessary permissions, and exposed test endpoints.

## Dynamic review
- Observe app behavior with synthetic accounts and data.
- Inspect traffic only where permitted and without collecting unrelated user information.
- Check whether logout clears session state, tokens expire, and authorization is enforced by the server.
- Test deep links and exported components using benign inputs in a lab.
- Check backup/restore and clipboard behavior where relevant.

## Defensive priorities
Use platform-supported secure storage, minimize permissions, disable debug features in release builds, validate intents and deep links, use modern TLS configuration, avoid sensitive logging, and enforce authorization on the server. Obfuscation does not replace sound security design.

## Exercise
Use an intentionally vulnerable Android training app. Document one manifest or storage issue, show why it matters with dummy data, apply a fix, and repeat the test. Keep all artifacts in your lab.
