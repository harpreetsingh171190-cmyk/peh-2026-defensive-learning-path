# Module 70 — Secure AI Red Teaming and Evaluation

## Scope
Evaluate AI applications you own or have explicit permission to assess. Use synthetic data and a staging environment. Do not attempt to extract real users' data or bypass safeguards on third-party services.

## Threat areas
- Prompt injection in user input or retrieved documents
- Sensitive data exposure
- Excessive agency or over-permissioned tools
- Unsafe output handling
- Retrieval and tenant-isolation failures
- Denial-of-service or unbounded cost
- Insecure model, plugin, or data supply chain

## Evaluation method
1. Write the intended behavior and prohibited outcomes.
2. Create benign, adversarial, and boundary test cases.
3. Use synthetic canary strings instead of real secrets.
4. Check whether untrusted content can change tool permissions or policy.
5. Verify output encoding and server-side authorization independently of the model.
6. Record expected result, observed result, severity, reproducibility, and fix.
7. Re-run the same tests after a change.

## Safe test examples
- Ask the app to summarize a document containing a clearly marked instruction to ignore the user's task; verify it treats that text as untrusted data.
- Supply a fake secret such as `TEST_SECRET_DO_NOT_USE_12345` and check that logging and responses do not expose it unexpectedly.
- Attempt a cross-tenant request only in a purpose-built local test fixture with two synthetic accounts.

## Key principle
A model response is not an authorization boundary. Enforce access control, tool permissions, and data filtering in deterministic application code.

## Deliverable
An AI evaluation matrix with test ID, threat category, synthetic input, expected behavior, observed behavior, risk, remediation, and regression-test ID.
